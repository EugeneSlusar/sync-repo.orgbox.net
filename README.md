# sync-repo

Универсальный Bash-скрипт для установки, настройки и синхронизации проекта с удалённым Git-репозиторием.

Скрипт помогает:

- инициализировать Git в проекте;
- подключить GitHub/GitLab-репозиторий;
- настроить ветку и авторизацию через SSH Deploy Key или токен;
- получить актуальный код и синхронизировать рабочую копию сервера.

Настройки и секреты сохраняются локально и не должны добавляться в Git.

В версии `1.4.7` (автонастройка появилась в `1.4.0`) пункт `3) Настроить автодеплой через GitHub Actions` настраивает GitHub
автоматически: мастер сам скачивает GitHub CLI (`gh`) в `.deploy/bin` без root-прав,
создаёт все secrets (`DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_PATH`,
`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`) и коммитит `.github/workflows/deploy.yml`
в рабочую ветку. Копировать значения вручную больше не нужно.
Нужен только fine-grained токен GitHub на этот репозиторий с правами Secrets, Contents
и Workflows (Read and write); токен запрашивается один раз и нигде не сохраняется
(можно передать через `GH_TOKEN`). Если автонастройка не удалась или выбран ответ «n»,
мастер показывает прежнюю инструкцию для ручной настройки.

В версии `1.3.14` отключён pager Git для всех вызовов внутри скрипта,
включая показ последнего коммита после синхронизации. Скрипт возвращает
приглашение терминала без экрана `less` с `(END)` и ожидания клавиши `q`.
Пользовательские настройки Git вне скрипта не изменяются.

Начиная с `1.3.13`, исполняемые временные файлы SSH и askpass создаются рядом
с локальным конфигом (обычно в `.deploy`), а не в `/tmp`: на виртуальном
хостинге `/tmp` может запрещать запуск файлов (`noexec`). Эти файлы исключены
из Git и удаляются при завершении скрипта, в том числе после ошибки подключения.

В версии `1.3.12` исправлен запуск на старом Git: если `rev-parse --git-path`
не поддерживается, путь к `info/exclude` определяется через `--git-dir`.
Для чтения remote предусмотрен обход отсутствующего `remote get-url`, а SSH
использует `GIT_SSH`, чтобы выбранный Deploy Key работал и без поддержки
`GIT_SSH_COMMAND`. Новые версии Git сохраняют корректную работу с worktree.
Восстановление локальных правок после подтверждения требует Git 2.23+;
на старом Git скрипт сообщает об этом и останавливается, сохраняя правки.

## Установка

Репозиторий публичный. Из корня проекта одной командой создайте каталог `.deploy` и скачайте туда скрипт:

```bash
mkdir -p .deploy && curl -fsSL -o .deploy/sync_repo_from_git.sh https://raw.githubusercontent.com/EugeneSlusar/sync-repo.orgbox.net/main/.deploy/sync_repo_from_git.sh
```

Установка и первый запуск вместе:

```bash
mkdir -p .deploy && curl -fsSL -o .deploy/sync_repo_from_git.sh https://raw.githubusercontent.com/EugeneSlusar/sync-repo.orgbox.net/main/.deploy/sync_repo_from_git.sh && bash .deploy/sync_repo_from_git.sh
```

## Запуск

Запустите скрипт из корня нужного проекта:

```bash
bash /path/to/.deploy/sync_repo_from_git.sh
```

По умолчанию проектом считается текущий каталог, а служебные настройки сохраняются в `.deploy/sync_repo_from_git.conf`. Каталог проекта можно указать явно через `GIT_REPO_DIR`.

Начиная с версии `1.3.8`, синхронизация не выполняет общую очистку файлов. Неотслеживаемые файлы, включая ядро Битрикса, загрузки и локальные настройки, сохраняются. Переменная `GIT_CLEAN=1` больше не включает удаление.

Начиная с `1.3.9`, при локальных изменениях отслеживаемых файлов интерактивный запуск показывает их список и спрашивает, восстановить ли версию из выбранной ветки репозитория. По умолчанию ответ — «Нет»: правки остаются на месте, обновление отменяется. При ответе «Да» скрипт сначала сохраняет резервную копию рабочих и индексированных правок в Git, затем восстанавливает файлы и продолжает деплой. Если резервную копию создать не удалось, правки не сбрасываются.

Начиная с `1.3.11`, перед этим вопросом автоматически выводится полный Git diff: рабочие изменения относительно индекса и, если есть, изменения после `git add` относительно локального `HEAD`. Это показывает локальные правки, а не изменения входящего коммита. Вывод идёт прямо в терминал, без pager, внешних diff-программ и textconv. Для бинарных файлов Git сообщает о различии без построчного diff. В режиме `--auto` остаются список изменённых файлов и остановка; содержимое правок не выводится.

Копии закрепляются ссылками `refs/sync-repo/backups/…`. Скрипт выводит ссылку и команду возврата `git stash apply --index <ссылка>`; применение поверх нового кода может потребовать разрешения конфликтов.

В режиме `--auto` локальные правки останавливают обновление без запроса и без сброса. Для подтверждения нужно один раз запустить скрипт интерактивно. Неопубликованные коммиты и конфликты путей с существующими неотслеживаемыми или игнорируемыми файлами также останавливают обновление: общая принудительная перезапись отключена.

Изменения файлов, которые отслеживаются Git, включая их удаление в целевой ветке, применяются при обычном обновлении. Настройки и секреты должны оставаться вне истории Git.

Для просмотра локальных правок:

```bash
git diff
git diff --cached
```

В дальнейшем этот инструмент станет основой для настройки автодеплоя: резервного копирования, миграций, перезапуска сервисов, проверки работоспособности и отката при ошибке.

## Интерактивное управление

При запуске экран очищается, затем скрипт последовательно запрашивает параметры обычным вводом и показывает итоговую таблицу перед синхронизацией.

При запуске в обычном проекте скрипт проверяет свежую версию в центральном репозитории. Начиная с `1.3.10`, если доступна более новая версия, интерактивный запуск показывает установленную и доступную версии и спрашивает, обновить ли сам скрипт. По умолчанию — «Нет»: работа продолжается с установленной версией. Та же или более старая версия не устанавливается. Скачанная версия не исполняется до подтверждения.

Перед заменой проверяется синтаксис Bash; после ответа «Да» скрипт заменяется и сразу перезапускается с исходными аргументами. В режиме `--auto` новая версия только показывается, а деплой продолжается установленным скриптом без ожидания ответа. В самом центральном репозитории проверка обновлений отключается автоматически. Для полного отключения проверки задайте `SYNC_REPO_AUTO_UPDATE=0`.

При переходе с `1.3.9` и более ранних версий первое самообновление ещё выполняется без вопроса по старой логике. Подтверждение действует после установки `1.3.10`.

При переходе с `1.3.7` рекомендуется сначала скачать новый скрипт отдельно и проверить `--version`: старая версия после самообновления продолжает текущий запуск со старой логикой.

Текущую версию можно узнать без запуска синхронизации:

```bash
bash .deploy/sync_repo_from_git.sh --version
```

Если репозиторий уже подключён, пункт `3) Настроить автодеплой через GitHub Actions` запускает полуавтоматический мастер на сервере. Мастер создаёт SSH-ключ и workflow, а затем показывает значения secrets, которые нужно один раз добавить в настройках GitHub.

Повторный запуск мастера не создаёт новый ключ, если Actions-ключ уже найден на сервере, поэтому существующие secrets можно использовать повторно.

Мастер также выводит полный текст workflow и инструкцию для добавления файла через GitHub Web: `Add file` → `Create new file` → `.github/workflows/deploy.yml` → `Commit changes` в `main`.

При настройке мастер красным предупреждает: SSH-ключи и `sync_repo_from_git.conf` нельзя добавлять в Git-репозиторий. Приватный Actions-ключ используется только как GitHub Secret.

Если проект ещё не подключён к Git, мастер предлагает подключить существующий репозиторий или создать новый GitHub-репозиторий из текущей папки. Для создания нужен установленный и авторизованный [GitHub CLI](https://cli.github.com/): `gh auth login`.

## Проверка

```bash
bash -n .deploy/sync_repo_from_git.sh
python3 tests/test_sync_repo.py
```

Тесты используют временные локальные Git-репозитории и подменяют сетевой запрос самообновления. Они проверяют обновление кода, первую установку, сохранность локальных данных, остановку при правках и конфликтах, а также самообновление.




Если `gh` не запускается из `.deploy/bin` (например, каталог проекта смонтирован с `noexec`),
мастер показывает текст ошибки и пробует `~/.local/bin`, `~/bin` и временный каталог.
Если `gh` падает в Go-рантайме из-за лимита потоков хостинга, мастер сам включает `GOMAXPROCS=1`.
Если токен не принят, мастер показывает ответ GitHub (например, `404 Not Found`) и убирает случайные пробелы из вставленного токена.

## Диагностика

- **«Git не установлен», а в логе `/dev/null: Permission denied`.** Git на месте, сломан `/dev`
  на сервере: у каталога `/dev` сброшены права (должно быть `drwxr-xr-x`, а не `drw-------`),
  из-за чего недоступны `/dev/null` и `/dev/ptmx` (не работают `git`, `mc`, скрипты). Обычный
  пользователь это не исправит: нужен root хостинга (`chmod 755 /dev`), обращайтесь в поддержку.
  Пока не починят, файлы можно скачать ZIP-архивом с GitHub и загрузить по SFTP.
- **Автонастройка GitHub Actions: `gh` не запускается.** Мастер пробует `.deploy/bin`,
  `~/.local/bin`, `~/bin` и временный каталог (часть каталогов бывает `noexec`), а при падении
  Go-рантайма включает `GOMAXPROCS=1` (лимит потоков на хостинге). Текст ошибки выводится на экран.
- **Токен не принят.** Нужен fine-grained токен: Resource owner — владелец репозитория,
  Repository access — этот репозиторий, права Secrets, Contents и Workflows (Read and write).
  Ответ GitHub показывается на экране; токен нигде не сохраняется.
- **Deploy key** (ключ репозитория) нужен серверу для `git pull` и лучше read-only. Автодеплой
  «GitHub → хостинг» делает GitHub Actions по SSH с отдельным Actions-ключом (его создаёт мастер).
